# Parallel scheduling, integration and cleanup

## Slots and eligibility

Default concurrency is three; record a user override as a positive integer. Count tickets from `registering` through `confirming`, including pending creations, review/repair and awaiting integration, against this work-in-flight limit. This bounds both active workers and the queue awaiting merge. Cleanup does not consume a worker slot once the worker is confirmed idle. A blocked worker releases its slot only after it is confirmed quiescent with no uncertain mutation; record it as parked. Resuming a parked worker requires a free slot. Preserve its dependency and overlap reservations even while parked.

Keep a dependency graph and a compact table of expected change areas per ticket. A queued ticket is eligible only when all prerequisites are verified on the named remote target, no unresolved prerequisite lies outside the batch, and its files/interfaces/resources do not foreseeably overlap any undelivered in-flight or parked ticket. Unknown scope requires bounded investigation. Do not make a broad global lock from a harmless shared read-only dependency. Use original ticket order or explicit priority to select eligible work.

On every actionable observation: reconcile pending actions, process completions, advance the integration holder, then fill available slots with eligible tickets. Do not wait for the whole first wave to finish. An uncertain creation holds one slot; an uncertain merge holds the integration reservation. A blocker holds only its affected dependency/conflict group unless it is demonstrably batch-wide. If no eligible work remains, record the precise recovery event instead of dispatching duplicates.

If workers discover overlapping edits, stop new dispatch into that area, have the lower-priority worker checkpoint and pause safely, and coordinate one owner until the first change is integrated. Retain both workers' work. Do not silently continue concurrent conflicting writers or discard a branch to resolve the overlap. Reassess dependencies, update the paused worker from the delivered target when safe, then resume within the limit.

## Worktree and resource isolation

Each worker has a dedicated worktree and owned working branch, normally `codex/…`, created from the user-selected target. Request `environment: {type: "worktree", startingState: {type: "branch", branchName: <actual target>}}` through `create_thread` after resolving the project. The initial assignment cannot require a branch name confirmed only after creation: instruct the worker to verify the generated branch or create a unique codex/ working branch in its dedicated worktree if detached/unassigned, then report its actual path and branch. Confirm ownership during registration. Verify the resulting checkout and branch rather than assuming setup used the latest remote tip. The worker must fetch and reconcile its starting point with the current remote target before editing; record that base SHA. Do not reset existing work during adoption or recovery.

Shared databases, ports, generated files and mutable test resources can conflict even across worktrees. Assign distinct local ports and synthetic databases/output directories where relevant. If a resource cannot be isolated, serialize its use explicitly. Read-only shared dependencies do not require separate copies.

## One integration reservation per target

Reserve integration for one accepted ticket, recording worker, PR/head or manifest, target revision and pending operation. Reserve this slot through preparation, merge and remote confirmation. Other workers can implement and be reviewed; none may merge independently. If a merge result is unknown, reconcile remote state before releasing the slot.

1. Send acceptance plus **preparation only** to the holder. It fetches the latest target, integrates that state without force-pushing history, resolves conflicts, performs required pre-merge OpenSpec validation/documentation (deferring pure closeout bookkeeping when policy allows), commits/pushes and prepares the PR against the exact target. It runs required checks and tests relevant to combined behavior, and returns the candidate head, target SHA and evidence. No merge yet.
2. Inspect the final candidate and compare it with accepted contents. Map bookkeeping-only differences explicitly; substantive changes require renewed evidence and acceptance. Recheck remote PR base/head, required checks and target tip. Acceptance is bound to candidate contents plus the tested target revision. If the target moved, keep the slot and request relevant revalidation against the new tip before issuing a merge grant.
3. Authorize only that PR/head against that target revision. The worker checks them again immediately before merging and stops for revalidation if either changed. No unattended auto-merge grant that can apply to a later unreviewed head. Use repository branch protection/native merge checks to enforce freshness where available; a coordinator reservation cannot lock out external writers.
4. Confirm actual remote merge and accepted contents on the user-selected target, including squash/rebase mapping. If external changes raced with merging, verify relevant combined behavior and required checks on the resulting target; do not claim the reservation prevented that race. A failed combined check blocks further integration until the worker repairs it and the result is verified. Release the reservation only after the delivery outcome is known. Confirm ticket closure; explicitly close a delivered ticket if the non-default target did not trigger auto-close.

Never change the target to main merely to make tool defaults or issue auto-close work. A delivered prerequisite can unlock dependent work while its cleanup continues. Cleanup failures do not retain the integration slot after confirmed delivery.

A ticket-specific blocker before a confirmed merge need not monopolize integration. To park the holder, reconcile that no merge is pending or uncertain, cancel its outstanding merge grant with an acknowledged worker message, confirm the worker is quiescent, and checkpoint the released reservation. If grant cancellation or mutation status is uncertain, retain the reservation. Another independently authorized candidate may then integrate; a batch-wide delivery-permission blocker still applies to all affected candidates. The parked worker needs a free work-in-flight slot, a new integration reservation and fresh head/target validation before resuming; an earlier grant never revives automatically.

## Guarded, resumable cleanup

The coordinator performs cleanup from a surviving checkout/directory after the worker is idle and no process still writes to its worktree. Do not ask a worker to remove its own active working directory. Keep these checkpointed outcomes separate: `evidence-preserved`, `worktree-removed`, `local-branch-removed`, `remote-branch-removed`, `worker-archived`.

1. Use `batch_state.py manifest`, `verify` and `retain` from [local-helpers.md](local-helpers.md) for explicit local artifact sets. The coordinator still establishes that the destination is outside **every** worker worktree and inspects the retained report. The helper does not authorize deletion. Copy acceptance evidence to a durable batch-owned directory outside every worker worktree, for example `<ledger-directory>/evidence/<ticket>/<accepted-revision>/`. Include the rendered report, screenshots/measurements and referenced assets needed to inspect it, plus accepted manifest, inspected conclusions and PR/merge mapping. Rewrite report links to durable destinations where needed. Verify copied files with hashes and open the retained report/images; update ledger links before deleting originals. An expired preview URL or links into the soon-deleted worktree are insufficient.
2. Re-read remote delivery, worktree ownership/path, worktree status, owned local/remote branch heads and worker status immediately before deletion. Require a known mapping of accepted contents to the actual merge (including squash), no additional unintegrated changes, and a clean worktree after approved evidence relocation. Unexpected files/commits or changed branch heads block their deletion pending investigation. Never delete the target, protected default branch, foreign worktrees/branches or unrelated user files.
3. Remove only the recorded owned worktree using normal Git worktree removal; never use a force-removal or broad recursive deletion to overcome unexpected contents. Remove the exact owned local and remote working branches only after proving all their intended changes are integrated. Prefer normal merged-branch deletion. For squash/rebase, an ancestry check alone may fail: establish the PR-head-to-merge mapping and absence of additional work, then use an expected-old-SHA guarded ref deletion. For a remote branch, use a lease checked against the recorded verified head when deleting, so a newly pushed commit is preserved. If the necessary proof or guarded operation is unavailable, record `cleanup-blocked` and retain the branch. This narrow conditional deletion is not permission to force-push history.
4. Verify actual worktree and branch absence, then archive the implementation task using `set_thread_archived`. Confirm archival from the returned result or a scoped archived-task lookup; absence from the ordinary recent-task list does not prove archival. Do not delete its history or the retained batch evidence. A task already archived or branch already removed is success only after verifying the intended object and the corresponding delivery/evidence gates; do not recreate it to replay cleanup.

Checkpoint before and after each mutation. After interruption reconcile each checklist item rather than repeating a deletion blindly. If cleanup is blocked, record the precise retained path/ref and cause; continue unrelated work and report the unfinished cleanup honestly. The batch is complete only after every ticket's delivery and cleanup checklist is satisfied, or the user explicitly narrows scope.
